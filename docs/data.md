# Data

Status: draft. This describes the target design; nothing is implemented yet.

The `orm` module gives applications a database layer that follows the same conventions as the rest of Balise. Following principle 7 ([architecture.md](architecture.md)), Balise owns everything the agent sees (models, queries, migrations, errors) and delegates the database wire protocols to existing drivers, which are never exposed.

Databases: PostgreSQL and SQLite in the MVP, MySQL later.

## One database per project

A project uses one database engine, set in `balise.toml` (`database = "postgres"`), and the same engine in dev, test and prod. Running SQLite in dev and PostgreSQL in prod is a classic trap: the engines behave differently and bugs only show up in prod. With Docker, PostgreSQL in dev costs nothing.

- No lowest common denominator: features that exist only in PostgreSQL (`ilike`, JSONB, arrays, full-text search) are available in a PostgreSQL project, and give a clear compile error in a SQLite project.
- Portability is Balise's problem, not the project's: Balise generates SQL for each engine, and a project only sees its own.

## Model pattern: explicit Active Record

Models carry their own persistence methods, in the Active Record style agents know best (Rails, Laravel, Django), without its hidden behavior:

- **Every method that touches the database takes `db` as a parameter.** No hidden or global connection. Wherever `db` appears there is a query, and only there: the agent and the audit can both see it.
- **No lazy loading.** Reading a field never triggers a query. Related rows are loaded explicitly.
- **Models are plain structs.** They hold data; persistence methods are generated by `#[derive(Model)]`.

Rejected alternatives:

- Data Mapper / repositories: clean separation, but more ceremony (a repository type per model, often a trait), more files, and more room for each agent to do it differently.
- Query builder without models: no magic, but nowhere to declare relations, constraints or the schema, and more code for the agent to write.

## Naming

The ORM uses the same verbs as handlers ([application.md](application.md#routes-and-handlers)): `list`, `get`, `create`, `update`, `delete`.

```rust
// src/orders/model.rs
#[derive(Model)]
struct Order {            // singular model, table `orders`
    id: OrderId,
    shop_id: ShopId,
    quantity: u32,
    note: Option<String>,
}

// src/orders/mod.rs
#[post("/shops/{shop_id}/orders")]
async fn create(shop_id: Path<ShopId>, input: Body<CreateOrder>, db: Db) -> Result<Created<OrderView>> {
    let order = Order::create(db, input).await?;
    Ok(Created(order.into()))
}

#[get("/orders/{id}")]
async fn get(id: Path<OrderId>, db: Db) -> Result<OrderView> {
    Ok(Order::get(db, *id).await?.into())     // missing row: 404
}
```

| Method | Purpose |
| --- | --- |
| `Order::get(db, id)` | the row, or an error that becomes a `404` |
| `Order::find(db, id)` | `Option<Order>`, when a missing row is expected |
| `Order::get_many(db, ids)` | several rows by id, in one query |
| `Order::list(db, page)` | a `Page<Order>` |
| `Order::query()` | filters, ordering, relations, then `.page(db, …)`, `.first(db)`… (see [Queries](#queries)) |
| `Order::create(db, input)` | insert from an `Input` |
| `order.update(db, input)` | partial update from an `Input` |
| `order.delete(db)` | delete |

- Models are singular (`Order`); tables are plural (`orders`).
- `get` and `find` are the only close pair of verbs, and they differ in behavior: pick `get` when a missing row is an error, `find` when it is a normal case.

## Three roles, three types

| Type | Role | Example |
| --- | --- | --- |
| `Input` | what comes in | `CreateOrder`, `UpdateOrder` |
| `Model` | what is stored | `Order` |
| `Output` | what goes out | `OrderView` |

- Conversions between them are generated when field names and types match: `Order::create(db, input)` accepts a `CreateOrder`, and `order.into()` produces an `OrderView`.
- **A model is never returned from a handler.** Returning an `Order` is a compile error pointing to `OrderView`. An agent cannot expose a field such as `password_hash` by accident.

## Schema: models are the source of truth

Models declare everything the database needs: columns, types, defaults, constraints, indexes, foreign keys. Migrations are generated from them. The goal is a model that expresses what SQL expresses, so the ORM layer is almost transparent while keeping its safety.

```rust
#[derive(Model)]
#[index(shop_id, created_at)]
struct Order {
    id: OrderId,
    #[field(references = Shop)]
    shop_id: ShopId,
    #[field(default = 1, check = "quantity > 0")]
    quantity: u32,
    #[field(unique)]
    reference: String,
    note: Option<String>,
}
```

- **Snapshot.** `schema.snapshot`, versioned with the code, records the schema as of the last migration. `balise migrate` compares the models with the snapshot, not with a live database: the diff is deterministic and works offline.
- **Drift check.** `balise check` fails if the models and the snapshot disagree, so a model change without its migration is caught.
- **Compile-time checks.** Queries are checked against the models' Rust types, with no database at compile time.
- **Generated SQL.** Balise writes the migration SQL for the project's database. The agent never writes DDL by hand.
- **Importing an existing database** (`balise db import`) is planned later, to start from a database that already exists.

Rejected alternatives: migrations as the source of truth (two places to edit for every change, DDL to write by hand), and the database as the source of truth (useful to take over a project, not to start one).

## Migrations can be edited

A generated migration is a starting point. The developer can edit it to decide what happens to existing data.

When a change needs data to be filled in (for example, a new required column whose value depends on another column), Balise generates the migration in three steps and leaves the middle one to write:

```sql
-- 0008_add_category.sql
-- generated: add the column as nullable
ALTER TABLE products ADD COLUMN category TEXT;

-- data: written by hand
UPDATE products SET category = CASE
    WHEN kind = 'X' THEN 'tools'
    WHEN kind = 'Y' THEN 'garden'
END;

-- generated: enforce the constraint
ALTER TABLE products ALTER COLUMN category SET NOT NULL;
```

- A migration with an unwritten data step cannot be applied: `balise migrate` stops with an error pointing to it.
- Data steps are written in the project's SQL dialect, and `balise check` runs them against a test database. A step too complex for SQL can be written in Rust, with the ORM, inside the migration's transaction.
- Generated steps handle each engine's limits (SQLite, for example, rebuilds the table to add a `NOT NULL` constraint).
- `balise migrate new --sql` creates an empty migration for anything the models cannot express.

## Renames

A rename is recorded in the migration history, never in the model: no `renamed_from` attribute, no dead code left after the migration.

- **A rename is an action, not a guess.** `balise rename orders.taille hauteur` (also an MCP tool) renames the field in the model, updates references in the code, and records the rename in the pending migration.
- **A manual rename is never guessed.** When a column disappears and another with a compatible type appears, `balise migrate` asks whether it is a rename or a drop and an add, in the terminal or through MCP. When nobody can answer (in CI), it stops with an error giving the exact flag: `--rename orders.taille=hauteur`.
- **Errors use the history.** When code uses an old name, `balise check` reads the migration history: "`taille` was renamed to `hauteur` in migration 0007".
- **Reusing an old name.** Renaming `taille` to `hauteur` and adding a new `taille` in the same change cannot be detected by a diff: it looks like "`taille` unchanged, `hauteur` added", and the old data would stay in `taille` with a new meaning. Two safeguards:
  - `AGENTS.md` requires `balise rename` for every rename, which records it before the new field exists;
  - every generated migration is summarized before it is applied ("add `hauteur`, keep `taille`, 1,240 rows kept"), so the mistake is visible before it happens.

## Queries

Queries are built with closures over a generated column struct: plain Rust, typed, no macro, with autocompletion on columns.

```rust
let orders = Order::query()
    .filter(|o| o.shop_id.eq(shop_id).and(o.quantity.gt(3)))
    .order_by(|o| o.created_at.desc())
    .page(db, page)
    .await?;
```

- Comparisons are methods (`eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `is_in`, `is_null`, `contains`, `starts_with`), combined with `.and()` and `.or()`. Rust's `==` must return a boolean, so it cannot build an SQL condition.
- Engine-specific operators (`ilike`, JSON paths, arrays) exist only when the project's engine supports them.

Terminal methods:

| Method | Returns |
| --- | --- |
| `.page(db, page)` | a `Page<T>` |
| `.first(db)` | `Option<T>` |
| `.one(db)` | exactly one row, otherwise an error |
| `.count(db)`, `.exists(db)` | a number, a boolean |
| `.limit(n).all(db)` | at most `n` rows |
| `.unbounded(reason).all(db)` | every row, deliberately |
| `.update(db, …)`, `.delete(db)` | bulk update or delete, with the number of rows affected |

**`.all(db)` exists only after `.limit(n)` or `.unbounded(reason)`.** A query without either is a compile error pointing to `.page()` or `.limit()`. The type system enforces it, no lint needed.

When loading everything is really intended, it is said explicitly: `.unbounded("export of all shops, run nightly")`. The reason is required, every unbounded query is listed in the audit, and adding one is flagged by `balise check` as a change that needs human approval.

Rejected alternatives: typed column constants (`order::Column::Quantity.gt(3)`: verbose, and the module name collides with the resource folder), and a macro translating Rust expressions into SQL (most natural to read, but a heavy macro with costly compile times and hard-to-read errors).

### Raw SQL

The escape hatch for what the builder cannot express:

```rust
#[derive(Row)]
struct ShopStats { shop_id: ShopId, revenue: i64 }

let stats: Vec<ShopStats> = db.sql("SELECT shop_id, SUM(total) AS revenue FROM orders WHERE created_at > $1 GROUP BY shop_id", (since,)).await?;
```

- `balise check` validates raw SQL against the schema snapshot (tables, columns, types), with no database.
- Every raw query is listed in the audit, so it stays an exception.

## Types

Every Rust type maps to one precise SQL type, visible, and specific to the project's engine. Balise does not invent abstract types: it frames how the database is used, it does not hide it.

### Default mapping

| Rust | PostgreSQL | SQLite |
| --- | --- | --- |
| `i16`, `i32`, `i64` | `smallint`, `integer`, `bigint` | `INTEGER` |
| `u32` | `bigint` + `CHECK (x >= 0)` | `INTEGER` + `CHECK (x >= 0)` |
| `bool` | `boolean` | `INTEGER` (0 or 1) |
| `f64` | `double precision` | `REAL` |
| `String` | `text` | `TEXT` |
| `String` with `max_length = 120` | `varchar(120)` | `TEXT` + `CHECK (length(x) <= 120)` |
| `Vec<u8>` | `bytea` | `BLOB` |
| `Decimal` | `numeric(p, s)` | not available |
| `Uuid` | `uuid` | `BLOB` (16 bytes) |
| `DateTime` (UTC instant) | `timestamptz` | `TEXT`, ISO 8601 |
| `Date`, `Time` | `date`, `time` | `TEXT`, ISO 8601 |
| `Json<T>` | `jsonb` | `TEXT` + `CHECK (json_valid(x))` |
| enum deriving `DbEnum` | `text` + `CHECK (x IN (…))` | `TEXT` + `CHECK (x IN (…))` |
| `Option<T>` | nullable column | nullable column |
| anything else | `NOT NULL` | `NOT NULL` |

Choices that are not obvious are shown, not hidden: PostgreSQL has no unsigned integers, so `u32` is stored as `bigint` with a constraint, and that constraint appears in the generated migration.

### Decisions

- **Enums** are stored as text with a `CHECK` constraint: easy to evolve (adding or removing a value is a constraint change), and identical on both engines. Native PostgreSQL enums are available on request (`#[db_enum(native)]`).
- **Dates on SQLite** are stored as ISO 8601 text: readable when the database is opened, and sortable.
- **`Decimal` is refused on SQLite**, with a compile error suggesting an integer amount in minor units (`total_cents: i64`). A decimal stored as text cannot be sorted or computed correctly in SQL.

### Engine-specific types

No lowest common denominator: types that exist in one engine are available under their real name, and only in projects that use that engine.

- PostgreSQL: `balise::pg::{Citext, Inet, Interval, TsVector, Range<T>}`, and `Vec<T>` for arrays.
- In a SQLite project, an array is a compile error suggesting `Json<Vec<T>>` or a child table.
- Last resort: `#[field(sql_type = "…")]` for an unusual type, with a Rust type that can read it.

### Guardrails

- **Money**: an `f64` on a field named `price`, `amount`, `total` or similar is flagged, with the fix: `Decimal` on PostgreSQL, integer minor units on SQLite.
- **Dates**: no "date and time without time zone" type by default. `DateTime` is always a UTC instant.
- **JSON**: `Json<T>` is typed with a struct. A frequent filter on a JSON field triggers a suggestion to make it a real column.
- **The JavaScript boundary**: integers above 2⁵³ lose precision in JavaScript. `Decimal` is sent as a string in JSON and typed as such in TypeScript; an `i64` above that limit raises an error instead of being silently corrupted.

### Transparency

- `balise schema` shows every model with, for each field, its exact SQL type and constraints.
- Migrations show the real SQL.
- MCP exposes the same information to agents.

## Conventions and constraints

### Identifiers

Every model gets a typed, prefixed UUIDv7 identifier by default.

- **UUIDv7**: not enumerable (no walking through `/orders/1`, `/orders/2`…), generated by the application so it is known before the insert, and ordered in time, so it stays efficient in indexes, unlike UUIDv4.
- **Typed**: `id: OrderId` (an alias of `Id<Order>`, generated with the model). Passing a shop's id where an order's id is expected is a compile error.
- **Prefixed in the API**: in JSON, logs and URLs the id reads `ord_01JB8X…`, while the database stores the raw UUID. Anyone reading a log knows what an id refers to, and TypeScript gets a distinct `OrderId` type. The prefix defaults to the first three letters of the model and can be set: `#[model(prefix = "ord")]`.
- **Integer on request**: `#[model(id = integer)]`, for internal tables where compactness matters. Its performance cost is measured in the [log of alternatives](alternatives.md).

### Timestamps

Every model has `created_at` and `updated_at`, filled in automatically. `#[model(no_timestamps)]` removes them.

### Soft delete

Opt-in, with `#[model(soft_delete)]`, which adds `deleted_at`.

- Queries exclude deleted rows by default; `.with_deleted()` includes them; `.purge()` deletes for real.
- Unique constraints become partial (`WHERE deleted_at IS NULL`), so a deleted account's email can be used again.

Why opt-in: keeping data that a user asked to delete is a legal and product decision, not a technical default. Personal data may have to be erased for real (GDPR), deleted rows keep growing tables and indexes, and cascades become ambiguous (does soft-deleting a shop soft-delete its orders?). Each model where it makes sense says so.

### Database names

All derived, none to write: tables plural and snake_case (`orders`, `product_tags`), columns named after fields, foreign keys `<model>_id`, and deterministic constraint and index names (`orders_reference_key`, `orders_quantity_check`, `orders_shop_id_created_at_idx`).

Every name can be set explicitly, for an irregular plural or an existing database:

```rust
#[model(table = "people")]
struct Person { … }

#[field(column = "qty", constraint = "legacy_qty_positive")]
quantity: u32,
```

### Constraints

Declared in the model:

| Constraint | Declaration |
| --- | --- |
| unique | `#[field(unique)]`, or `#[unique(shop_id, reference)]` on the model |
| check | `#[field(check = "quantity > 0")]` |
| foreign key | `#[field(references = Shop, on_delete = restrict)]` |
| default | `#[field(default = 1)]` |
| index | `#[index(shop_id, created_at)]` on the model |

Check expressions are written in the project's SQL dialect and validated against the schema snapshot.

### Constraint violations

Constraint names lead back to fields, so every violation becomes a Balise error naming the field:

| Violation | Response |
| --- | --- |
| unique | `409`: "`reference` already exists" |
| foreign key on insert | `422`: "`shop_id`: shop `shp_…` does not exist" |
| foreign key on delete | `409`: "the shop still has 12 orders" |
| check | `422`: the field and the rule |

### Constraints declared once

An `Input` whose fields match a model inherits the model's constraints. `max_length = 120` or `check = "quantity > 0"` on `Order` apply automatically to `CreateOrder`, then to the validation generated for the front end ([web.md](web.md#forms)). A rule declared once in the model protects the database, the API and the form.

- An `Input` can add rules, never loosen them.
- Checks that cannot be translated outside SQL stay database-only, and their violation is still reported on the right field.

## Relations

### Declaring

Relations are deduced from foreign keys: `#[field(references = Shop)] shop_id` on `Order` creates `order.shop` and `shop.orders`. The foreign key is the single source of truth.

Declaring the relation on the other side is optional, for readability:

```rust
#[derive(Model)]
#[has_many(Order)]          // optional: makes `shop.orders` visible in Shop's definition
struct Shop { id: ShopId, name: String }
```

- An optional declaration must match a foreign key: a `has_many` with no matching key is a compile error.
- Two keys to the same table (`author_id` and `reviewer_id` to `User`) are ambiguous: Balise refuses to compile until each one is named (`#[field(references = User, as = "reviews")]`).
- Many-to-many relations always go through an explicit join model (`ProductTag`), which can carry its own columns.

### Loaded data

A relation field knows whether it was loaded:

```rust
let shop = Shop::query().with(|s| s.orders.limit(20)).one(db).await?;
let orders = shop.orders.get()?;       // loaded: the orders
```

If the relation was not loaded, `.get()` returns an error with the fix ("add `.with(|s| s.orders)` on line 42"). Reading a relation never runs a hidden query.

### Loading strategy

Balise chooses how to load each relation: a join for a relation to one row (`order.shop`), one query with `IN (…)` per relation to many rows (`shop.orders`). The number of queries depends on the number of relation levels, never on the number of rows.

### N+1 queries

Automatic batching (DataLoader style) only works for queries sent at the same time. A loop that awaits `Shop::get` on each iteration sends them one after the other, and nothing can merge them afterwards. So no magic, but three tools:

- `.with()` for relations;
- `Shop::get_many(db, ids)` for a list of ids;
- N+1 detection in dev, which suggests one of the two with the exact line.

The default `.with()` works, and Balise says when it is not the best approach.

### Bounded relations

Loading a relation to many rows follows the same rule as queries: `.with(|s| s.orders.limit(20))`, or `.unbounded(reason)` when loading everything is intended. Without either, it is a compile error.

### Loading driven by the output (experimental)

An `Output` already declares what it needs, so it can drive the loading:

```rust
#[derive(Output)]
#[output(from = Shop)]
struct ShopView {
    name: String,
    orders: Vec<OrderView>,      // needs the orders relation
}

#[get("/shops")]
async fn list(db: Db, page: Query<PageParams>) -> Result<Page<ShopView>> {
    ShopView::query().page(db, page).await       // loads exactly what ShopView uses
}
```

`ShopView::query()` loads only the columns and relations the view uses, with the best strategy. When the goal is to read data and return it, there is no `.with()` to write, no relation to forget, and nothing loaded for nothing: N+1 queries and over-fetching disappear by construction. `.with()` remains for business logic on models.

This is not how developers usually approach the problem, so:

- it is documented with examples in [application.md](application.md) and `AGENTS.md`, and taught by the generators;
- agent evaluations measure whether agents use it ([agent-experience.md](agent-experience.md#evaluating-the-agent-experience));
- it is dropped if it does not catch on in practice. `.with()` alone covers every case.

### Expected table size

In dev, tables hold a few rows, and production warnings are rarely read. So the size that matters is declared where the agent works, in the model, as an order of magnitude:

```rust
#[derive(Model)]
#[model(expected_rows = "1M")]       // 1k, 10k, 100k, 1M, 10M…
struct Order { … }
```

The declaration is optional. When present, it drives:

- the priority of static findings: a missing index or a `contains` on a table declared at `1M` is a warning, not information;
- pagination advice: on a large PostgreSQL table, `.with_total()` triggers a suggestion to use `.with_estimated_total()`, and `.page_numbered()` a warning about distant pages;
- the audit at scale: `balise audit --scale` fills each table to its declared size instead of one global number;
- accepted findings: an `.accept()` is reconsidered when the declared or measured size grows tenfold.

When the audit or production statistics measure a size far from the declared one, Balise suggests updating the declaration. Production findings are also brought back into the dev loop: `balise audit --from-prod` imports production query statistics, so they surface where the agent works instead of in logs nobody reads.

## Pagination

Two modes, cursor by default:

| Method | Mode | Use |
| --- | --- | --- |
| `.page(db, params)` | cursor | feeds, infinite scroll, APIs: constant cost, stable when rows are added |
| `.page_numbered(db, params)` | offset, with total | admin screens with page numbers: its name says it has a cost |

- **Deterministic order.** Balise always adds `id` as the last sort key. UUIDv7 ids are ordered in time, so sorting by creation date is sorting by `id`: the most common case is also the most efficient.
- **Opaque, checked cursors.** A cursor encodes the sort values of the last row and the sort order. A modified cursor, or one reused with another order, returns a `422` with a clear code.
- **Totals on request.** `.with_total()` adds a total to cursor pagination; on PostgreSQL, `.with_estimated_total()` gives a fast estimate.
- **Limits.** 20 items per page by default, 100 at most, set in `balise.toml`. A larger `per_page` sent by a client is lowered to the maximum.
- **Per-route override.** Like file sizes, a route that needs other limits declares them, without changing the others:

  ```rust
  #[get("/exports/orders", page(default = 500, max = 5000))]
  ```

Responses:

- cursor: `{ items, next_cursor, prev_cursor, has_more }`;
- numbered: `{ items, page, per_page, total, total_pages }`.

The generated client knows each route's mode and limits: infinite scroll for cursor routes, page controls for numbered ones ([web.md](web.md)).

## Writes and transactions

### Lazy transaction per request

Every request runs in a transaction that opens lazily:

- it opens at the first write;
- it commits when the handler succeeds, and rolls back when it returns an error;
- a handler that only reads never opens one.

A handler that writes to two tables is atomic without the agent thinking about it, and read-only handlers pay nothing. `db.transaction(|tx| …)` stays available for background tasks and fine control. Dev instrumentation flags a network call made while a transaction is open.

### Side effects after commit

When a transaction is open, `channels.publish()` and `balise::spawn()` are deferred until it commits. If it rolls back, they never run: no email or realtime event for data that was never saved.

### Partial updates

```rust
#[derive(Input)]
#[input(patch)]
struct UpdateOrder {
    quantity: u32,
    note: Option<String>,
}
```

With `#[input(patch)]`, every field becomes optional: an absent field is left unchanged, and `null` clears a nullable field. The agent writes plain types; Balise generates the rest, TypeScript included. `order.update(db, input)` writes only the fields that were sent.

### Updates in business logic

```rust
order.update(db, |o| o.status = Status::Paid).await?;
```

One verb, `update`, accepts an `Input` or a closure. With a closure, Balise compares before and after and writes only what changed. There is no `save()`.

### Concurrent writes

- Atomic operations for read-modify-write: `|o| o.stock.decrement(1)` generates `SET stock = stock - 1`, together with a constraint such as `check = "stock >= 0"`.
- Dev instrumentation detects the "read, then write back a computed value" pattern on numeric columns and suggests the atomic form.
- Optional optimistic locking with `#[model(versioned)]`, for models edited by several people at once.

### Bulk writes and conflicts

| Method | Purpose |
| --- | --- |
| `Order::create_many(db, inputs)` | insert many rows in one query |
| `Order::query().filter(…).update(db, …)` | bulk update |
| `Order::query().filter(…).delete(db)` | bulk delete |
| `Order::upsert(db, input, \|o\| o.reference)` | insert, or update on a unique key |

- A bulk update or delete without a filter follows the rule of `.all()`: it needs `.unbounded(reason)`.
- A unique violation becomes a `409` naming the field.
- Inserts return the full row, including values set by the database (`RETURNING`).

### Deletes and cascades

The foreign key declares what happens on delete: `#[field(references = Shop, on_delete = restrict)]`, with `restrict`, `cascade` or `set_null`. The default is `restrict`: deleting a shop that still has orders fails with a clear error instead of erasing data silently.

## Non-optimal queries

A non-optimal query is not always a slow one: the real risk is a query that takes 2 ms in dev with 20 rows and 4 s in prod with 2 million. Balise knows the models (indexes, relations), the queries (built through its API) and the outputs (what each `Output` actually reads), so it can find problems before they show.

### Four levels

1. **Static analysis** (`balise check`, no database): filter or sort on a column without an index, foreign key without an index (Balise creates one by default), `contains` that cannot use an index, function applied to a column in a filter, and the same checks on raw SQL against the snapshot. These are **candidates**, not verdicts (see below).
2. **Dev instrumentation**, per HTTP request, with each SQL query fingerprinted by its shape:
   - N+1: the same shape executed N times with different values;
   - duplicates: the same query with the same values, twice;
   - writes in a loop, to replace with a bulk insert;
   - over-fetching: columns loaded that the `Output` never reads;
   - an `EXPLAIN` once per new shape, translated into plain words ("full scan of `orders` for a filter on `status`");
   - a transaction held open during a network call.
3. **Audit at scale**: `balise audit --scale 100000` fills a test database with realistic volume through factories, replays the scenarios, and compares:
   - execution plans, which often change with volume;
   - the number of queries as data grows: if it grows, it is a hidden N+1;
   - offset pagination on distant pages, and costly `COUNT(*)` on large tables.
4. **Production, later**: lightweight tracking of query shapes per handler (frequency, duration), to spot what drifts under real traffic.

### Helping to fix

- Every finding points to the line in application code that ran the query, not to the framework: terminal methods such as `.page()` capture their call site (`#[track_caller]`).
- Every finding is a `PERF` event with a concrete fix: "add `#[index(status)]` on `Order` (orders/model.rs:3)", or "add `.with(|o| o.items)` on line 42".
- Safe fixes can be applied directly: `balise fix PERF0012` adds the index to the model and generates the migration.
- The audit measures before and after, so the agent sees whether its fix helped.

### Keeping the signal clean

A `LIKE '%…%'` is sometimes the right choice, an index on everything slows writes, and a large project must not drown important messages under warnings it has carried for months.

- **Static findings are candidates.** On their own they are shown as information. They become warnings only when they matter: because the table is declared large (see [Expected table size](#expected-table-size)), or because the audit at scale or production statistics measured it. A `contains` on a 200-row table is not reported.
- **Index suggestions weigh their cost.** Balise does not suggest an index on a low-cardinality column (a boolean, a status with three values), and lowers the priority on write-heavy tables.
- **Accepting a finding is explicit, local and justified**, next to the query:

  ```rust
  Product::query()
      .filter(|p| p.name.contains(term))
      .accept(PERF0007, "name search on a table capped at 10k rows")
  ```

  The reason is required. Like budgets, adding an `accept` is flagged by `balise check` as a change that needs human approval, so an agent cannot silence a finding on its own.
- **An accepted finding comes back when its context changes.** Balise records the table size at the time it was accepted; if the audit later measures ten times more rows, the finding is reported again.
- **Baseline for existing projects.** `balise check --baseline` records current findings in `perf-baseline.toml`. Only new findings are reported; the baseline shrinks as findings are fixed.
- **Ranked output.** `balise check` shows errors first, then new warnings, then one summary line for the rest ("97 known findings, see `balise audit`").

## Drivers

Delegated and invisible. The first option that works is used to start; tokio-postgres with rusqlite and sqlx-core are compared later, in the log of alternatives ([alternatives.md](alternatives.md)). SQLite calls run on the blocking pool so they never hold the event loop. A driver is rewritten only if a measurement justifies it.

## Test data

### Factories derived from models

`Order::fake()` builds a valid row that respects the model's types, `CHECK` constraints, unique constraints and foreign keys, creating the parent shop if needed. Values are realistic based on field names (`email`, `name`, `price`). Nobody writes factories by hand; tests only state what matters:

```rust
let order = Order::fake().with(|o| o.quantity = 3).create(db).await?;
```

`Input` types get the same: `CreateOrder::fake()` builds a valid request body for API tests.

Factories and seeds exist only in dev and test builds, never in the production binary.

### Reproducible

Fake data comes from a seed. The same seed gives the same data, so a failing test replays identically, for the agent as for a human. The seed is printed when a test fails.

### Seeded dev database

`balise new` generates a `dev` dataset: the front end shows credible data from the first run instead of empty pages, so a screen can be judged at a glance. `balise seed <name>` loads a named dataset, defined in `src/seeds/<name>.rs` with the same factories.

### Data at scale

The audit at scale ([Non-optimal queries](#non-optimal-queries)) fills each table to its declared size, with uneven distributions: a few shops with a huge number of orders, many with very few. Uniform data hides real problems. Rows are inserted in bulk (`COPY` on PostgreSQL) to stay fast.

### Generated validation tests

Rules are declared in models and `Input` types, so Balise generates the tests that check them: an invalid value is rejected with the right code and field, and the boundary value is accepted.

### Test isolation

Each test gets a fresh database, copied from a template database on PostgreSQL, in memory on SQLite ([environments.md](environments.md#test)). Rolling back a transaction at the end of each test is often faster; both are compared in the [log of alternatives](alternatives.md).

### Later: anonymized copy of production

A `#[field(personal)]` attribute would mark personal data, and serve three purposes: redaction in logs, real erasure for GDPR, and `balise db snapshot --anonymize` to work on a copy of production without personal data.

## Production feedback

Production reports ([errors-and-logs.md](errors-and-logs.md#production-findings)) bring real table sizes, index usage and costly queries back into the dev loop. When a measured size is far from `expected_rows`, Balise suggests updating the declaration.
