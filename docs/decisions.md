# Decisions

Status: living document.

Decisions taken while building Balise, with their reason. Most recent last. Options still to be measured live in the [log of alternatives](alternatives.md).

| Date | Decision | Reason |
| --- | --- | --- |
| 2026-10-10 | Crate names `balise` and `balise-*` reserved on crates.io, including `balise-macros` | Route attributes and derives need a separate proc-macro crate, so its name is reserved with the others |
| 2026-10-10 | npm scope `@balise-rs` for front-end packages (`@balise-rs/react`…) | `@balise` and the unscoped `balise` are taken on npm |
| 2026-10-10 | GitHub organization `balise-rs` | `balise` is taken on GitHub; same name as the npm scope, one identity everywhere |
| 2026-10-10 | Error codes declared with a `macro_rules!` in `balise-core/src/error_codes/`, one file per area prefix | No build script or parser, so no compile cost; one file per area keeps the registry readable |
| 2026-10-10 | Each code is a typed constant (`error_codes::EXT0001`) that only the registry can create | Raising an unregistered code from Rust does not compile; a test scanning the sources catches the rest (strings, comments) |
| 2026-10-10 | No doc page per error code: `balise explain` and MCP read the explanation from the registry | A page would repeat the registry; agents get the same text without leaving the loop. A website can be generated from the registry later if needed |
| 2026-10-10 | Compile benchmark results kept in the CI cache, each commit compared with the previous one, instead of stored per commit | Enough to catch a regression when it lands, without a results branch or a CI token |
| 2026-10-10 | Compile-time slowdowns are warnings, never failures | Timings vary between runs; a flaky failure teaches to retry, not to fix |
| 2026-10-10 | `balise new` enables every optional module, listed explicitly in the project's `Cargo.toml`; `--no-<module>` refuses one | A new project works end to end out of the box; the list in `Cargo.toml` says what the project uses |
| 2026-10-10 | Without `orm`, the generated example is a route and a page, with no storage | Storage is the agent's job then; an in-memory example would teach a pattern to avoid |
| 2026-10-10 | No published image for now: the dev environment is the `dev` stage of the project's `Dockerfile`, built by `compose.yaml` | Nothing to publish or version while the toolchain changes; dev and production builds share one base. A published image comes later: on Docker Hub, `balise` is taken and `balise-rs` is invalid (no hyphens), `balisers` is free |
| 2026-10-10 | `main.rs` declares one `mod` per resource, added by `balise generate resource`; `balise check` reports a resource folder that is not declared | Rust needs the declaration; a forgotten module means routes that silently do not exist. `main.rs` declares modules, not routes |
| 2026-10-10 | Seeds live in `src/seeds/`; seeds and factories compile only in dev and test builds | Cargo only builds `src/`; datasets have nothing to do in the production binary (no dev-only code in prod) |
| 2026-10-10 | The API prefix (`/api` by default, version included, such as `/api/v1`) is set in `balise.toml` and never written in route attributes | Routes stay the same whatever the prefix; changing it is one line |
| 2026-10-10 | Inputs and outputs of a resource live in its `api.rs`; `model.rs` holds only the model | `api.rs` is the contract with the front end, the one TypeScript is generated from |
| 2026-10-10 | Budgets are keyed by handler (`orders::list`), not by URL | Changing the API prefix or a path does not invalidate them |
| 2026-10-10 | The facade has a `test` feature, enabled by `balise test` | Test builds differ from dev builds at compile time (counters for budgets) |
| 2026-10-10 | One npm package, `@balise-rs/react`, also provides the Vite plugin and the lint configuration | Fewer packages to install and version; split later only if useful |
| 2026-10-10 | One dev supervisor in the CLI: `balise dev --inside` in the container, `balise dev --native` on the host; the host's `balise dev` only starts Docker and relays | One binary to write; supervision, rebuilds and logs are the same with or without Docker |
| 2026-10-10 | Agent hooks call `balise check --hook` / `balise audit --hook`, which speak the agent's hook protocol | A plain command would run on every edit and its errors would not reach the agent. To verify on a real project (log of alternatives) |
| 2026-10-10 | Auth routes generated in `src/auth/`; the `User` model generated in `src/users/model.rs` and owned by the application, checked by `#[auth::user]` | Rust has no inheritance: a model provided by the module could not get new fields |
| 2026-10-10 | Default budgets deduced from each route's shape; `budgets.toml` only holds overrides | Defaults are not duplicated in every project, and improving them reaches existing projects |
| 2026-10-11 | `create` takes an `Input` or a closure, like `update`; `.set()` combines both; a required field given by none is an error naming it | One verb for every way to build a row, and missing fields are caught early |
| 2026-10-11 | Ownership declared in the model (`owned_by`, `owned_through`, `public`), enforced at compile time by `.owned_by(owner)` or `.all_owners(reason)`; `get` answers `404` for someone else's row; `Owner` only from `CurrentUser` or `Owner::trusted` | Forgetting the owner filter (IDOR) is the easiest handler mistake; the compiler catches it. Part of the ORM, so it works with any authentication |
| 2026-10-11 | `Db` is `Copy`, a handle to the request's context | Used several times per handler without borrowing or cloning |
| 2026-10-11 | `.one()` with no row answers `404` (`DB0042`), like `get` | A missing row behaves the same whatever the method |
| 2026-10-11 | Generators write `pub`; `balise check` explains visibility errors (E0616, E0603) | Models and inputs live in submodules; a missing `pub` is a frequent agent error |
| 2026-10-11 | `AppError` declared in `api.rs`; application codes have four digits (`ORD0001`) | Error codes are part of the contract with the front end; same format as Balise's codes |
| 2026-10-11 | Pagination parameters come from `Query<PageParams>`; `Page<Order>` converts into `Page<OrderView>` with `.into()` | Reuses the existing extractor and conversion, no new concept |
| 2026-10-11 | Helpers about one model are methods in `model.rs`; handler helpers stay in `mod.rs`. Helpers shared between resources: to decide when the case comes | No `utils/` folder, and each helper has an obvious place |
| 2026-10-11 | `id`, `created_at` and `updated_at` are declared in the model, written by generators and recognized by name; removing the timestamp fields replaces `no_timestamps` | Everything stored is visible in `model.rs`; one rule less |
| 2026-10-11 | Model and `Input` rules add up; a detectable contradiction is a compile error | A rule declared once protects everything, and an input can only tighten it |
| 2026-10-11 | One `#[derive(Enum)]` for models, inputs, outputs and TypeScript, same value in the database and in JSON | One way to declare an enum |
| 2026-10-11 | The current user's output is `CurrentUserView` | `CurrentUser` is the extractor; consistent with the `*View` convention |
| 2026-10-11 | Test paths have no API prefix, the test client adds it; bodies are typed (`.body(input)`, `CreateOrder::fake()`); `balise::test::json!` only for invalid bodies | Same paths as route attributes; typed bodies follow the API; no delegated `serde_json` in user code |
| 2026-10-11 | `sign_in_as_new_user` compiles only with both `auth` and `test` | The core never assumes an optional module |
| 2026-10-11 | A `mail` module: captured in dev (`/_balise/mails`, `mails` MCP tool), SMTP in production; without it, `auth` calls a hook the application implements | The agent can test the reset flow on its own; email is needed by `auth` |
| 2026-10-11 | Sign-in through `User::authenticate(db, email, password)`, same error and timing whether the email exists or not | Accounts cannot be probed (to confirm in the auth step) |
| 2026-10-11 | `.owned_by(&user)` is the documented form; `Owner` is a `Copy` marked id; in dev and test, `&User` is accepted too; factories are exempt from ownership | `CurrentUser` holds data and cannot be `Copy`; one syntax in handlers, seeds and tests |
| 2026-10-11 | Responses are checked with their type first (`res.json::<OrderView>()`); `assert_json_includes(json!(…))` for partial checks | A renamed field breaks at compile time; the name says the check is partial |
| 2026-10-11 | `Mailer` is a handler parameter; `send()` is deferred after commit; tests read mails with `app.mails()` | Consistent with `Db` and `State`; no mail for a rolled-back write; the reset flow is testable |
| 2026-10-11 | Draft migrations: a migration can be rewritten until `balise build` freezes it in a versioned file; in dev, the database is rebuilt from drafts and seeds | Balise cannot see production, so "never deployed" must be recorded; removing a resource or squashing becomes one mechanism |
| 2026-10-11 | `balise remove resource <name>`, symmetric to `generate`; the example resource teaches it, and removing the example suggests `balise generate` | Removing the example takes one command instead of hunting it across back end, front end, seeds and migrations |
| 2026-10-11 | Seeds stay central and front routes stay in `App.tsx` | Collecting them per resource would add mechanisms for little gain; `balise remove` handles the cleanup |
| 2026-10-11 | `balise new --no-example` | For those who already know what they want |
| 2026-10-11 | The reference project is generated from the mock-up's `orders`, copied and renamed per resource, rather than from a separate template | One source: the reference project follows the mock-up automatically |
| 2026-10-11 | Reference project: 8 resources plus `users` and `auth` (54 routes, 9 models), without realtime for now | A realistic routes-to-models ratio without a second template to maintain; realtime is added once the mock-up has a channel |
| 2026-10-11 | A `5xx` is an `error` event plus the request line; a `4xx` has no separate event, the request line carries its code, detail and location | A `4xx` is the API working as designed; logging it as an error would bury real failures (bots probing ids) |
| 2026-10-11 | Logs may say more than the response (a `404` on another user's row says so in logs only) | The server needs the reason to debug; the client must not learn that the row exists |
| 2026-10-11 | Prod `5xx` responses carry a generic `HTTP0500`, a generic message and the request ID; `4xx` responses keep their code and message | Infrastructure details stay on the server; the request ID links the client's report to the logs |
| 2026-10-11 | Expected outputs live in `mockup/outputs/` and become the renderer's reference tests | The mock-up becomes a specification the implementation is checked against |
| 2026-10-11 | `balise check` reports where the fix goes, not where rustc points; `--hook` prints the terminal text without colors on stderr | The agent edits the right line; plain text costs fewer tokens than JSON |
| 2026-10-11 | In the terminal, every `fix:` line is followed by `more: balise explain CODE`; the request ID goes on the `at` line | One rule for where `explain` appears; the request ID and the doc command are separate concepts |
| 2026-10-11 | A request line reads as a sentence: `POST /api/orders → request req_… (orders::create returned 500 in 5004 ms with 0 queries)` | Explicit for a human and an agent, no symbols to decode |
| 2026-10-11 | Ownership messages name the owner (`which user's rows`) | "whose" did not say who |
| 2026-10-11 | Reference outputs are compared byte for byte at the renderer level, with fixed event values; end-to-end tests replace times, ids and durations with placeholders | The renderer is a pure function; only end-to-end runs vary |
| 2026-10-11 | `Page::map(f)`, synchronous, keeps the cursor; `.into()` stays for direct conversions | A per-row query cannot be written in the closure; the agent never rebuilds a page by hand |
| 2026-10-11 | Generators wrap what they add outside a resource's folders in `balise:<resource>` markers; `balise remove` deletes marked blocks, reports edited ones, refuses when another resource depends on it | Reliable removal without parsing TypeScript or Rust |
| 2026-10-11 | `page.ids()`, `.index_by(key)` and `.group_by(key)` for bulk-loaded data that is not a relation | Cheap to provide; avoids a hand-written `HashMap` written ten ways. `.with()` stays the way for relations |
| 2026-10-11 | Reference outputs are checked at three levels: renderer (byte for byte), end to end on the mock-up's routes (normalized), compile errors on a test project | Formatting alone does not prove that a real error has the right location, code and cause |
| 2026-10-11 | MCP tools answer with compact text in `content` and the same data as JSON in `structuredContent` | The model reads the text; JSON costs 1.5 to 2 times more tokens for the same information |
| 2026-10-11 | `project_map` has two levels: one line per route and model, or the details of one resource | The overview stays around 2,000 tokens for 50 routes; the agent reads details only where it works |
| 2026-10-11 | `explain` takes a code or a topic (pagination, budgets…), topics declared in a registry like codes | Some questions have no error code; one tool, one registry |
| 2026-10-11 | `explain` topics live in the error registry, one file per topic | One registry for everything `balise explain` shows |
| 2026-10-11 | One validation code, `VAL0001`, with per-field details in `fields` | A 422 has one meaning; the fields say what is wrong |
| 2026-10-11 | `project_map()` falls back to one line per resource beyond about 3,000 tokens | Keeps the overview cheap on large projects; details stay one call away |
| 2026-10-11 | `project_map()` lists what modules add for the agent (tools, dev pages) | Otherwise the agent only learns about them from `AGENTS.md` |
| 2026-10-11 | Types are linked explicitly: `#[output(from = Order)]` generates the conversion by field name; `#[input(model = Order)]` calls hidden per-field validation functions generated by the model; contradictions between rules are reported by `balise check` | A derive only sees its own struct; the link is also readable in the code. Replaces "conversions generated when names match" |
| 2026-10-11 | `create` takes only a generated `NewOrder { … }` literal, without the fields the database fills; the owner field is an `OwnerId<User>` built from `user.owner()`, not deserializable | A missing field is rustc's E0063; an `Input` never reaches the database as a whole, so mass assignment, owner included, is impossible. Replaces `create` with an `Input`, a closure or `.set()` |
| 2026-10-11 | `update` takes a closure over `&mut Order`; atomic operations go through a query (`.update(db, \|p\| p.stock.decrement(1))`) | Plain assignments in the closure; column expressions only where SQL computes the value |
| 2026-10-11 | `Patch<T>`, one type for every field of a partial update; `null` on a non-nullable field is a `422`; the derive generates `apply_to` | A derive cannot change field types, and `Option<T>` cannot tell absent from `null`. Replaces `#[input(patch)]` |
| 2026-10-11 | Relations are explicit fields: `BelongsTo<Shop>` replaces `shop_id` (`.id()` always, `.get()?` once loaded); `HasMany<Order>` must match a `BelongsTo` | A plain struct needs a place for loaded relations; consistent with explicit `id` and timestamps. Replaces "relations deduced from foreign keys" |
| 2026-10-11 | Hallucination traps: `balise check` rewrites rustc's E0599 / E0412 from its JSON output; `#[diagnostic::on_unimplemented]` for a few trait-bound cases | E0599 cannot carry a custom message, and trait bounds on concrete types do not compile on stable |
| 2026-10-11 | The query typestate only tracks boundedness (`limit`, `page`, `unbounded`), which comes last; filters keep the type, so `if` works | Conditional query building must type-check |
| 2026-10-11 | `AppError` types do not implement `std::error::Error`, so their generated `From` does not overlap the general one | `?` works on every error without specialization, as in `anyhow` |
| 2026-10-11 | The query type tracks two end-of-chain states, bounded and scope chosen; `.owned_by()` and `.all_owners()` lead to the same state; a missing scope is reported through `on_unimplemented` with a code; public models start scoped; `get`, `find`, `update`, `delete` on an owned model need the scope too | The ownership guarantee holds at compile time, with no shortcut, and conditional scopes still compile |
| 2026-10-11 | A loaded relation is read with `.loaded()` (`&User`, `&[Item]`); reading one that was not loaded panics with a code; no `Deref` | A missing `.with()` is a programming error; conversions to outputs stay a plain `.into()`, no `try_map`. `get` would suggest an `Option` |
| 2026-10-11 | `NewOrder` holds only the required fields; fields with a declared default are set with `.with_<field>()`, which returns an `Insert<Order>`; managed fields (`id`, timestamps) have none; `NewOrder { status: … }` (E0560) is rewritten by `balise check` | A struct literal must list every field; one form for optional values |
| 2026-10-11 | The owner field is checked: `owned_by = User` needs `BelongsTo<User>`, `owned_through = order` needs `BelongsTo<Order>` to an owned model | Parent and child are settled by the compiler, not by documentation |
| 2026-10-11 | No ownership bypass: owned relations loaded from a public parent need a scope; `upsert` keys include the owner; raw SQL on an owned table goes through `raw_unscoped(reason, …)` | Each path to an owned row keeps the guarantee |
| 2026-10-11 | `.owned_by(&User)` in dev and test is dropped; no public API changes with the build profile, except dev and test tooling (rule in AGENTS.md) | Code that passes the agent loop must compile in release. Replaces the dev/test-only `&User` |
| 2026-10-11 | Several owners (marketplace, teams) are outside the MVP; `Owner` stays generic internally | Not needed now, not blocked later |
| 2026-10-11 | Read-check-write needs a lock in the types: `.for_update()` returns a `Locked<Order>`; `update`, `delete` and `apply_to` exist only on it; generators write it in `update` and `delete` handlers; deadlocks get their own code | A compile error gives one deterministic fix, where a warning asks the agent to judge; the handler keeps the shape agents write |
| 2026-10-11 | Conditional updates are for atomic counters only; optimistic locking (`versioned`) goes to the log of alternatives | Each mechanism has one use; no third way in the MVP |
| 2026-10-11 | `db.independent()` for writes that survive a failed request: a second connection on PostgreSQL, queued until the request's transaction ends on SQLite | Sign-in attempts and rate limits must not be rolled back; SQLite has one writer |
| 2026-10-11 | Side effects by cost of loss: `publish` from memory after commit; `mailer.send()` through a `balise_outbox` table in the transaction (at least once, stable `Message-ID`, `SKIP LOCKED`), from memory without `orm`; `db.after_commit` explicit; `spawn` never deferred | A lost reset mail is a bug, a lost realtime event is not; `spawn` keeps one meaning |
| 2026-10-11 | `spawn(\|db\| …)` gives the task its own `Db` with request rules; a request's `Db` used after its request is a runtime error with a code; the source scan of `balise check` is a warning only | The runtime check is the real guarantee; a lifetime on `Db` would break rule 3 |
| 2026-10-11 | Handlers run in their own task and finish when the client disconnects; route timeouts still cancel | Disconnection must not leave half-done work; a timeout that cannot cancel protects from nothing |
| 2026-10-11 | One draft migration, regenerated freely, frozen by `balise migrate freeze`; `balise check --ci` fails on a draft, release builds refuse one; staging and prod apply frozen migrations only | Freezing at `balise build` did not match how code reaches production. Replaces freezing by `balise build` |
| 2026-10-11 | `balise migrate` classifies changes as compatible or breaking; breaking ones are split over two versions or approved as a deploy with downtime | Migrations at startup stay safe during rolling deploys |
| 2026-10-11 | `balise migrate` is never interactive: an ambiguity fails with a code and ready-to-paste flags | An agent's shell cannot answer a prompt |
| 2026-10-11 | Data steps written in Rust use `db.sql` with row structs declared in the migration, never the models; their SQL is checked against that migration's snapshot | A migration must compile forever; models change after it is written |
| 2026-10-11 | Sensitive decisions (budget, accept, unbounded, all_owners, raw_unscoped, breaking migration, dependency) follow `.balise/policy.toml`, `human` or `agent` per type, changed only by `balise policy set` in a terminal; presets `autonomous` (default), `strict`, `full-auto`; every decision recorded in `.balise/approvals.toml` with a fingerprint of the normalized content; CI fails while one is pending | Human approval was never defined, and an end-of-task hook blocking on it looped. Each project chooses how autonomous its agent is, and every decision stays traceable |
| 2026-10-11 | MCP tools are served by what they need: `search_api`, `explain` and `check` by the CLI, `project_map` from the last successful build (`stale_since`), live tools by the dev server; the CLI downloads the index of the project's Balise version | The agent keeps its tools when the code does not compile |
| 2026-10-11 | `cargo test` works through `[dev-dependencies]` with the `test` feature; `balise test` starts the test database; `balise check --ci` builds the release configuration | Respect the agents' habit; catch release-only errors |
| 2026-10-11 | Every test request checks its route's budget; `assert_queries_at_most` is removed | Budgets live in one place, and a test cannot raise one |
| 2026-10-11 | `logs` joins the MVP; `balise audit` reports runtime errors and `PERF` seen in dev since the last audit | Runtime problems reach the agent without being looked for |
| 2026-10-11 | Two levels of checks: incremental after each edit (short output, cancelled by a new edit), full at the end of a task; CI checks everything | Multi-file changes are not interrupted; slow checks run once per task |
| 2026-10-11 | Framework rule: no warning on correct code; a pattern right in most cases becomes the default or goes into the types | A warning asks the agent to judge; it over-corrects or learns to ignore warnings |
| 2026-10-11 | `balise::run()` is synchronous and returns `!`: it creates the multi-threaded Tokio runtime, and reports fatal startup errors with their code before exiting | No `#[tokio::main]` and no `Result` in the application's `main` |
| 2026-10-11 | The engine speaks HTTP/1.1 only until built-in TLS | What proxies use towards the app; fewer dependencies, faster builds |
| 2026-10-11 | Client-side connection errors are `debug` events (`HTTP0002`) | They are not errors of the server, like `4xx` |
| 2026-10-11 | Balise's own lockfile follows the 7-day release age it imposes on projects (hyper, syn and smallvec pinned to older versions) | Same supply-chain safety for the framework as for its users |
| 2026-10-11 | Rule 1 is checked by a test: the facade depends on no delegated crate and its source never names one | Rustdoc's JSON output, which lists the public API exactly, needs nightly |
| 2026-10-11 | One code per cause of a listening failure (port in use, permission, address not available, other), its own code for a runtime that cannot start and for running out of file descriptors; out of file descriptors, the server waits before accepting again and reports at most once per second with a count | A fix must match its cause; a retry loop without a pause floods the logs and burns the CPU |
| 2026-10-11 | Rule 4 of AGENTS.md: `EXT0001` only for what Balise cannot classify | Using it for known situations hides the fix the code exists to give |
| 2026-10-11 | The router is entirely Balise's: a tree of path segments, static segments before parameters, the first route accepting the method wins, `405` with `Allow` otherwise, strict paths | Its answers are what the agent sees (`404`, `405`, `balise why`) |
| 2026-10-11 | Route collection through `linkme`, wrapped in `balise_core::registry`; the macros only reach it through `balise::__private` | Invisible to the agent, so delegated; nothing runs before `main`; replaceable in one place |
| 2026-10-11 | `Config` is the single source of the address and the API base (`api.prefix`, optional `api.version` giving `/api/v1`); a test forbids these literals elsewhere | No hard-coded `/api` to miss when configuration arrives |
| 2026-10-11 | A route lives in the resource of what it returns; a nested handler is named `<verb>_in_<parent>` (`list_in_shop`) | The name two of three blind agents guessed |
| 2026-10-11 | Handlers are called through two internal traits, `FromRequest` and `IntoResponse`, with no public implementation until extractors and responses exist | Routing is tested end to end without freezing a temporary API |
| 2026-10-11 | The route macro uses `syn` 3, like `linkme` | One `syn` to compile in every project instead of two |
| 2026-10-11 | The 7-day release age is enforced for projects (pnpm natively, `balise add` for crates), not for the framework's own lockfiles: `tools/release-age` reports young versions in CI, with the command to pin them, without failing | Cargo cannot select versions by age, and pinning by hand at every update costs more than it protects here |
