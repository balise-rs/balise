# Environments

Status: draft. Environments and configuration are implemented; the rest describes the target design.

This document covers the three environments (dev, test, prod), configuration, Docker, and production builds.

## Three environments

The environments differ from compile time, not only through a variable: dev tooling does not exist in the production binary.

| | Dev | Test | Prod |
| --- | --- | --- | --- |
| Build | debug, feature `dev` | debug, feature `test` | release, without `dev` |
| MCP server | yes | no | absent from the binary |
| Instrumentation | full (N+1, query plans, blocked event loop) | counters for budgets | lightweight metrics |
| Logs | readable, colored | JSON | JSON on stdout |
| HTTP errors | detailed page, cause and fix | detailed | generic message and request ID |
| Migrations | one draft, regenerated by `balise migrate`; rewriting it rebuilds the database, then seeds | database recreated | frozen migrations only, applied under a lock |
| Supervision | `balise` CLI | test runner | orchestrator |

`BALISE_ENV` selects the environment: `dev`, `test` or `prod`. Without it, the environment is the one the binary was built for: `dev` with the `dev` feature, `test` with the `test` feature, `prod` otherwise. A binary built with `dev` refuses to start with `BALISE_ENV=prod` (`CFG0004`), so a dev build cannot reach production by mistake.

## Configuration

Sources, from highest to lowest priority:

1. environment variables (`BALISE_` prefix, plus `DATABASE_URL` and `PORT`);
2. the `[env.<name>]` section of `balise.toml`;
3. the top level of `balise.toml`;
4. Balise's defaults.

- `balise.toml` sits next to `Cargo.toml` and is embedded in the binary by `balise::run!()`: the production image holds only the binary. Changing the file means rebuilding; what differs between deployments goes in environment variables.
- A setting's variable is `BALISE_` followed by its key in capitals, dots becoming `_`: `log.level` is `BALISE_LOG_LEVEL`. A few settings also read a common name: `PORT`. An unknown `BALISE_` variable is reported like an unknown key.
- Every message about a value says where it comes from: a line of `balise.toml` (and its `[env.…]` section), or a variable.
- Secrets are never written in `balise.toml` (`CFG0005`). They come from environment variables, or from a file through the `_FILE` suffix (`DATABASE_URL_FILE=/run/secrets/db`), which matches Docker and Kubernetes secrets. A secret's value never appears in a message.
- Validation rules (strict in dev, fail at startup in prod for security and data settings) are described in [engine.md](engine.md#configuration).
- The app's binary checks a configuration without starting: `./app config check --env prod`, exit code `0` or `1`. It applies the strictest rules whatever the environment: what only warns at a production startup is an error here. Run it in CI; `balise config check` runs it for you.
- Modules declare their own settings (`database` for `orm`…); a module's keys exist only when it is enabled.

| Setting | Default | Variable |
| --- | --- | --- |
| `host` | `0.0.0.0` | `BALISE_HOST` |
| `port` | `3000` | `BALISE_PORT`, `PORT` |
| `api.prefix` | `/api` | `BALISE_API_PREFIX` |
| `api.version` | none | `BALISE_API_VERSION` |
| `limits.body_size` | `2MB` | `BALISE_LIMITS_BODY_SIZE` |
| `limits.timeout` | `30s` | `BALISE_LIMITS_TIMEOUT` |
| `shutdown.timeout` | `10s` | `BALISE_SHUTDOWN_TIMEOUT` |
| `storage.dir` | `storage` | `BALISE_STORAGE_DIR` |
| `pagination.per_page` | `20` | `BALISE_PAGINATION_PER_PAGE` |
| `pagination.max_per_page` | `100` | `BALISE_PAGINATION_MAX_PER_PAGE` |
| `log.format` | `text` in dev, `json` in test and prod | `BALISE_LOG_FORMAT` |
| `log.level` | `info` | `BALISE_LOG_LEVEL` |

Error details in responses are not a setting: they follow the environment (on in dev and test), so they cannot be turned on in production by mistake.

## On the host

The only thing to install is the `balise` launcher, once per machine; it fetches the CLI of each project's Balise version by itself ([agent-experience.md](agent-experience.md#a-launcher-and-a-cli-per-version)). For now it is installed with `cargo install balise`, which needs Rust. Later, an install script, Homebrew and `cargo binstall` will fetch a prebuilt static binary, and Rust will not be needed on the host.

## Dev with Docker

`balise new` generates `compose.yaml`, a `Dockerfile` whose `dev` stage is the dev image, and `rust-toolchain.toml`. `balise dev` starts:

- the application, in the `dev` stage (Rust at the version of `rust-toolchain.toml`, the CLI of the project's version), with reload;
- later, the database (PostgreSQL, or a volume for SQLite) and the Vite dev server ([web.md](web.md#dev-server-and-vite)), with the modules that need them.

Practical points:

- The code is not in the image: the project is mounted at `/app`. The image only holds Rust and the CLI; its build context is `rust-toolchain.toml` alone (`.dockerignore`), and it is rebuilt when the toolchain or Balise's version changes.
- `target/` and the Cargo registry are named volumes. Without them, every restart recompiles everything; on macOS and Windows, files mounted from the host are slow, and `target/` stays inside the container. `balise dev stop` keeps them.
- `compose.yaml` holds no setting of its own. `balise dev` reads the port and `shutdown.timeout` from `balise.toml` and gives them to compose as variables: the port is published on `127.0.0.1` only, and `stop_grace_period` is `shutdown.timeout` plus 5 s. Run `docker compose` by hand and it stops, asking for `balise dev`. The container's environment does not inherit the machine's variables: only the files count.
- The container runs as the user of the machine, so that what the app writes in the project belongs to them.
- `balise dev` relays the container's logs until Ctrl-C, which stops the app cleanly; a second Ctrl-C kills it. `--detach` runs it in the background: `balise dev status` says whether the app answers, `balise dev stop` stops it. Before starting, `balise dev` checks that Docker is installed (`DEV0004`) and running (`DEV0005`), and that the port is free (`DEV0006`).
- With `balise new --balise-path`, to work on Balise itself, the container mounts the local checkout at the same path and builds its CLI from it at each start, instead of installing a published one.
- The agent reaches MCP through `balise mcp` on the host, which relays to the dev server in the container. The agent never deals with Docker ([agent-experience.md](agent-experience.md#mcp)).
- `balise dev --native` skips Docker when Rust is installed on the host.
- `balise check` compiles on the host when Rust is installed there, and in the dev container otherwise: the running one (`docker compose exec`), or a temporary one. It says so, since it is slower.
- One supervisor, wherever the app runs: inside the container, the `dev` stage runs `balise dev --inside`, the same CLI at the project's version. It watches files, rebuilds, restarts the app, runs Vite and merges every log into one stream. On the host, `balise dev` only starts `docker compose` and relays logs and MCP. `balise dev --native` runs the same supervisor directly on the host.
- The supervisor reads the files' dates every 300 ms, which works through the mount between the machine and a container, where notifications from the system do not always arrive. A change rebuilds with `--features dev`; while the build runs, or when it fails (`DEV0002`), the last version that built keeps answering. Once built, the app is stopped as an orchestrator stops it (`SIGTERM`, then its graceful shutdown) and started again. Once it accepts connections, the supervisor says `Ready:` with the API's address, at each start.
- An app that stops on its own is reported (`DEV0001`) and started again, unless it stopped right after starting: then the supervisor waits for a change instead of failing in a loop.
- The dev journal: an app built with `dev`, and the supervisor, append every event, and what routing decided for each request (route, parameters, limits), to `.balise/dev/journal.jsonl` in the project, ignored by git. `balise logs` and `balise trace` read it, whether the app runs or not; on the machine, also when the app runs in the container. It keeps the last few megabytes. A production build does not compile its writer.
- Commands that read the project (`balise routes`, `balise why`, `balise config check`) build the app with `dev`, then run it with the command. Like `balise check`, they run in the dev container when the machine has no Rust.

## Test

- `balise test` runs the test suite in the `test` environment.
- Each test gets a fresh database: a copy of a template database on PostgreSQL, an in-memory database on SQLite.
- Query counters are on, so budgets can fail tests ([agent-experience.md](agent-experience.md#budgets)).

## Production build

`balise build` produces one binary that contains the server, the application, and the front-end assets.

- Static binary (musl target) with mimalloc as the global allocator, because musl's allocator collapses under a multi-threaded runtime.
- Generated multi-stage `Dockerfile`: a dependency-caching stage (cargo-chef), a build stage, and a minimal final image (`scratch` or distroless) containing only the binary. A few MB.
- rustls uses the `ring` crypto provider, which avoids a C toolchain when cross-compiling.

## Running in production

What the binary provides for orchestrators (Docker, systemd, Kubernetes):

- `/health` (process alive) and `/ready` (ready for traffic), at the root;
- graceful shutdown on `SIGTERM`, for `shutdown.timeout` at most; the orchestrator's grace period must be longer ([engine.md](engine.md#shutdown));
- JSON logs on stdout;
- the crash report of a panic that stopped the previous run, published at startup, from `storage.dir`;
- a summary of findings for agents in `balise-findings.json`, and `./app report` to export it with the database's real sizes ([errors-and-logs.md](errors-and-logs.md#production-findings));
- migrations applied at startup under a PostgreSQL advisory lock, so several instances starting together do not race. Only frozen migrations reach production, and only compatible changes are applied during a rolling deploy; a breaking change is split over two versions or approved as a deploy with downtime ([data.md](data.md#compatible-and-breaking-changes)). A setting makes startup fail instead when a migration is pending, for teams that migrate in a separate step.

The orchestrator restarts the process after a crash; Balise does not supervise itself in production.

Optional, for small deployments without a reverse proxy: built-in TLS with automatic certificates (ACME).

## Open questions

From the review of the mock-up by agents (2026-10-11):

- **The `FROM scratch` image** has no writable folder for `storage.dir` (uploads are streamed to `<storage.dir>/.uploads`, then stored there), no CA certificates (SMTP, outgoing HTTPS), and runs as root. A distroless static image, or `scratch` with these added and a non-root user.

- Scope of a future `balise deploy` command (which targets).
- Metrics format in production (Prometheus endpoint, OpenTelemetry, or both).
