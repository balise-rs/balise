# shop

A web application built with Balise, a Rust web framework designed for coding agents.
Its API is not in your training data: look it up, never guess it.

## Before writing code

- Look up the project with the MCP tools: `project_map` (routes, models, inputs, outputs), `search_api` (Balise's API).
- Without MCP: `balise introspect`, and `llms.txt` for the API reference.
- Create resources with `balise generate resource <name> --front`, then fill in the generated files.

## Working loop

1. After each change, run `balise check`. It compiles the back end and the front end and explains each error.
2. Run the tests with `balise test` (it starts the test database; `cargo test` also works when it runs).
3. After each feature, run `balise audit` and fix every warning. It also lists the runtime errors seen in dev.
4. Unclear error code: `balise explain <CODE>`.

The dev server: `balise dev --detach` starts it in the background, `balise dev status` and `balise dev stop` control it, `balise logs` shows its recent events.

`balise check` replaces `cargo check`, `tsc` and the linter: use it instead.

## Layout

```
src/
  main.rs           declares the resources and starts the app; nothing else goes here
  orders/           one folder per resource
    mod.rs          handlers
    api.rs          inputs and outputs: the contract with the front end
    model.rs        model
    tests.rs        tests
  auth/             sign-in routes, generated: adapt them as needed
  users/            the User model: add your own fields
  seeds/            datasets for `balise seed`, dev and tests only
migrations/         generated by `balise migrate`, editable
frontend/src/
  balise/           generated client: never edit
  pages/<resource>/ pages
```

## Rules

- Handlers are short verbs (`list`, `get`, `create`, `update`, `delete`) in their resource folder.
- Route paths never include the API prefix: write `#[get("/orders")]`, served at `/api/orders`.
- Return an `Output` type or a wrapper (`Created`, `NoContent`, `Page`); never a model, never a status number.
- Lists are paginated: return `Page<T>`.
- Every database call takes `db`. Change models, then run `balise migrate`; never write DDL by hand.
- No `static mut`, global state, `std::sync::Mutex`, `RefCell`, `tokio::spawn` or `println!`: use `State`, `Shared`, `balise::spawn` and `balise::log`.
- Front end: call the API only through `frontend/src/balise`; never `fetch` `/api` directly.
- Add a dependency with `balise add <package>`, never by editing `Cargo.toml` or `package.json`.
- Rename a model field with `balise rename <model>.<field> <new>`, never by hand: the migration must know it is a rename.
- Lines between `balise:<resource>` and `/balise:<resource>` markers belong to generators: keep them together, so `balise remove resource` can find them.
- Some changes are decisions, not fixes: raising a budget, `.accept`, `.unbounded`, `.all_owners`, `raw_unscoped`, a breaking migration, a new dependency. `.balise/policy.toml` says who takes each one. When it is the user, tell them to run `balise approve`; when it is you, use the `approve` tool with a reason. Never edit `.balise/policy.toml` or `.balise/approvals.toml`.

## This project

Modules: `orm` (PostgreSQL), `auth` (cookie sessions), `mail` (captured in dev: `/_balise/mails`). Front end: React.

## Debugging

Investigate through Balise, never inside its dependencies: `balise routes`, `balise why GET /api/orders/1`, `balise trace <request_id>`, `balise logs`.
Production problems: ask the user to run `./app report` and share the file, then `balise audit --from-prod report.json`.
